# SDK query sessions and freshness

The explorer must never execute a request with a different SDK than the one named by its cache key. A network change or same-network reconnect must also retire outstanding requests and inspector side effects immediately. (Trust changes no longer happen: untrusted mode was removed in #40, and the `trusted` key segment is always `true`.)

## Design

`SdkProvider` assigns a unique session ID and abort signal to every connection attempt. The outgoing signal is aborted synchronously before network or reconnect changes; reconnect also clears the old SDK. Superseded connection results are ignored, and unmount aborts the current session. Session IDs remain unique across provider remounts.

One low-level `useSdkQuery` wrapper owns readiness, cache keys, and cancellation. Keys use `['npe', network, trusted, sessionId, ...methodKey]`; caller options can disable execution but cannot force an unready SDK to execute. The query captures its ready SDK instead of polling a mutable SDK reference. Session abortion cancels the exact React Query request. Since the SDK cannot abort all its requests, the execution guard also rejects delayed results and suppresses inspector records and fallback requests from retired sessions.

The proof-aware wrapper retains proof transport and capture behavior while delegating the lifecycle boundary to the same low-level wrapper used by write forms. Proof classification improvements are a separate change.

Documents fetched by ID have 30-second freshness because their revisions can change. Deterministic validation and finalized epoch queries remain indefinitely fresh. Platform status now polls every 30 seconds, matching Core status. Core queries wait for a ready network selection, and health is unknown while the SDK is connecting or unavailable.

Confirmed writes call `invalidateNetworkQueries(client, submittedNetwork)`. The network prefix invalidates all session variants, including balances, nonces, schemas, and list queries whose relationships cannot safely be inferred from one receipt. Transaction-shell wiring is a separate change. Failed or uncertain writes must not use this confirmation helper.

Network-aware links synchronize `?network=` during client navigation through a small `useSearchParams` component with its own Suspense boundary. Unknown URL networks stop SDK execution and show an accessible error; selecting a configured network repairs the parameter. History updates use Next's supported `replaceState(null, ...)` path to keep router search parameters synchronized.

Initial selection follows URL, valid saved preference, then configured default precedence. The saved custom-network registry is loaded before validation, so custom devnet defaults and links work. Unknown configured defaults or explicit selections never create an SDK using `getNetwork`'s display fallback. Their visible errors remain blocked until a configured network is selected; removing an invalid URL only restores a known selection. Browser storage is optional: blocked getters/reads use configured defaults, stale saved names are ignored, and failed writes leave the selected network active in memory.

## Session resilience

Every session is trusted. The SDK cannot run proof-bearing queries without a trusted context (untrusted builds fail with "Non-trusted mode is not supported in WASM"; `proofs: false` panicked the WASM module in 4.0.0-rc.2 and is refused with a Config error in 5.0), so the untrusted toggle and `NEXT_PUBLIC_TRUSTED_MODE` were removed and a saved `npe:trusted` is deleted on load. Sessions are built with `new EvoSDK(buildSdkOptions(...))`, which carries the locally stored connection settings (SDK `settings`, `logs`) and an optional quorum-service override. Mainnet/Testnet sessions pass no DAPI addresses and use the quorum service's masternode list, so the quorum URL is the supported way to use other endpoints. Devnets pass their DAPI addresses and quorum URL when their configuration has them. (In 4.0.0-rc.2 the trusted context replaced explicit addresses; since evo-sdk 5.0 explicit addresses win, so a devnet's saved addresses are the endpoints it uses.)

`connect()` (quorum prefetch) has an explorer deadline (`startupTimeoutMs`, default 20 s). A failed or timed-out session sets `status: 'error'` with an `SdkSessionError` (`unknown-network`, `timeout`, `unreachable`, `failed`). Caller-enabled queries without data then report that error (their `refetch` reconnects), instead of staying pending, and `SdkSessionNotice` shows a page-level "Cannot reach Dash Platform" state with Settings as the alternate-endpoint action. A query error saying no DAPI address is left sets the session's `unreachable` flag without discarding it; the next successful query or a reconnect clears it. While a session is not ready, `refetch()` is a no-op so React Query cannot cache a "not ready" error under the session key.

When the session ID changes, `SdkProvider` removes every cache entry of retired sessions. That drops the last references to their SDK, which wasm-bindgen's FinalizationRegistry then frees. Instances that were never published (superseded or timed out) are freed explicitly once their `connect()` settles; published ones are not, because freeing an instance with a request in flight fails that request with "null pointer passed to rust". Paginated reads (evonode blocks) check session retirement before and after every page.

Errors are classified by SDK kind and message (`classifySdkError`): definite absences (EpochNotFound, TotalCreditsNotFound, IdentityNonceNotFound) become a `null` result so pages render not-found states, while a generic NotFound for a dependency stays an error and a gRPC NOT_FOUND from one node is retryable transport (#40); timeouts and transport failures are retryable unavailability; a quorum missing from the trusted context is unavailable, not a failed proof, blocks the ordinary-method fallback, and offers Reconnect (since 5.0 the SDK first asks the quorum service for the missing key itself); only explicit or unrecognized native proof errors are verification failures. The global retry policy retries once only for timeouts, transport and unknown errors.

## Validation

Regression tests cover readiness options, delayed proof responses across network and reconnect changes, cancellation without stale evidence or fallback, mutable document freshness, idle Platform polling, network-scoped invalidation, superseded connections, reconnect reset, unmount, URL hydration/navigation, and invalid-link recovery. Chromium tests run the production export through network selection, search, operation navigation, reload, and invalid-link recovery using Next's actual patched history implementation. Client navigation also preserves the existing document and settings control while updating the mounted provider. These browser flows do not require live DAPI success; delayed-response cancellation and polling are tested with controlled SDK fixtures.
